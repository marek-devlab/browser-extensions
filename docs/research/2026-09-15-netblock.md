# Research: Request Blocker — расширение №16 (рабочее имя `extensions/netblock`)

> **Версия 1** (2026-09-15). Слой исследования для нового расширения: блокировка/фейл сетевых запросов по правилам пользователя — по типу ресурса, имени/URL, HTTP-методу, **коду ответа**, заголовкам и **по последовательности** (N-й запрос, «B после A», «один раз», окно после события).
>
> Сделано четырьмя параллельными раундами deep-research (Chrome MV3 · Firefox MV3/Android · обзор инструментов · политики сторов + stateful-архитектура). Источники — только 2024–2026: developer.chrome.com (страницы с пометкой «updated 2026-09-11»), исходники Chromium/mozilla-central (main/tip на 2026-09-15), MDN/BCD, Bugzilla, WECG, Extension Workshop, Mozilla Add-ons Blog; исходники Requestly/Netify/uBO; **скачанные CRX-пакеты** Requestly v26.7.27, tweak v9.1.0, Resource Override MV3, Network Overrides API v2.3.0 (манифесты — как «жёсткое» свидетельство того, что сейчас проходит ревью CWS).
>
> Конвенции документа те же, что в [`PLAN.md`](../../PLAN.md): ⚠️ — факт, ломающий «очевидную» архитектуру; 🔴 — запрет. Код этим документом не пишется; статус — в [`TODO.md`](../../TODO.md).

## 0. Итог одним экраном

| Решение | Значение |
|---|---|
| **Цель одной фразой** | «Блокировать и фейлить сетевые запросы по правилам — для тестирования отказоустойчивости фронтенда» (dev/QA-инструмент). Narrow focus area по Quality Guidelines FAQ (2025-01): лог запросов, счётчики срабатываний и редактор правил — функции *той же* темы, допустимы |
| ⚠️ **Главный факт** | **Ни DNR (Chrome), ни DNR (Firefox) не умеют условие по коду ответа** — статус не заголовок, поля нет, предложений в WECG нет. В Chrome единственные пути к «если 500»: `chrome.debugger` (CDP `Fetch`, стадия Response) или патч `fetch`/XHR в MAIN-world. В Firefox — штатно: `{cancel:true}` из blocking `onHeadersReceived` по `statusCode` |
| ⚠️ **Второй факт** | **Ни в одном из существующих расширений нет готовых stateful-правил** (N-й, once, после события). Модель берём из MSW (`once`), Playwright (`times`), Dev Proxy (`nth`), MockServer chaos (`succeedFirst`/`failRequestCount`/`outageAfterMillis`/`seed`), WireMock scenarios (state machine) |
| **Архитектура** | **Один формат правила — три движка** (`engine: auto \| dnr \| page \| debugger`), движок выбирается как самый дешёвый, который *гарантированно* выполнит критерий; UI честно показывает, какой активен и почему. Firefox — четвёртый движок `webrequest`, покрывающий всё |
| **Chrome: без чего нельзя** | `declarativeNetRequest` (block без host permissions), `webRequest` (наблюдение: `statusCode`, `ERR_BLOCKED_BY_CLIENT`), `scripting` (MAIN-world инъекция), `storage`, `alarms`; `optional_host_permissions: <all_urls>` + «включить на этом сайте»; **`debugger` — только `optional_permissions`**, включается кнопкой на конкретной вкладке («Network-level mode») |
| **Firefox** | `webRequest` + `webRequestBlocking` + `<all_urls>` (как в `adblock`), event page, `gecko_android: {}`, `data_collection_permissions.required: ["none"]`. Один движок закрывает все критерии, включая статус и последовательности, без гонок |
| 🔴 **Нельзя** | `declarativeNetRequestFeedback` в сторе (игнорируется для CWS-установок, даёт warning «Read your browsing history» → Purple Potassium); пользовательский JS в правилах через `eval`/`new Function` (Blue Argon); в Firefox-сборке — `userScripts` вообще (AMO: «только для user script managers»); delay через сервер вендора; `modifyHeaders`, ослабляющий CSP (AMO §-политика) |
| **Что ещё не проверено** | Латентность `updateSessionRules`; ловит ли CDP `Fetch` WebSocket-хендшейк; поведение при одновременно открытых DevTools и `debugger.attach` (документация и код Chromium расходятся) — см. §9 |

## 1. Критерии → реализуемость (главная матрица)

Условные обозначения: **да** — детерминированно; **частично** — best effort с оговоркой; **нет** — механизм не умеет.

| Критерий | Chrome: DNR | Chrome: webRequest-наблюдение → session DNR | Chrome: MAIN-world патч fetch/XHR | Chrome: `debugger` + CDP Fetch | Firefox: blocking webRequest |
|---|---|---|---|---|---|
| Тип ресурса (script/xhr/image/font/ws/…) | да (`resourceTypes`; fetch = `xmlhttprequest`) | да | только XHR/fetch (+WS, EventSource; `sendBeacon` можно лишь сломать) | да (WS — не подтверждено, §9) | да (`filter.types`; есть `beacon`, `imageset`, `json` 138+) |
| URL: подстрока / glob | да (`urlFilter`, `*`, `\|`, `\|\|`, `^`; только ASCII/punycode) | да | да | да (`urlPattern` с `*`/`?`) | да |
| URL: regex | частично (RE2, ≤1000 regex-правил, ≤2 KB, без lookahead) | частично | да (JS RegExp) | да (JS RegExp) | да |
| Домен / инициатор / top-frame | да (`requestDomains`, `initiatorDomains`, `topDomains` **Chrome 145+**, `domainType`) | да | да | да | да (`originUrl`, `documentUrl`, `thirdParty`) |
| HTTP-метод | да (`requestMethods`, 91+) | да | да | да | да |
| Заголовки **запроса** (условие) | нет (WECG #964 — предложение gorhill 2026-03, не реализовано) | частично (видно в `onBeforeSendHeaders`, блок только *будущих*) | да | да (+ `postData`) | да (`cancel` в `onBeforeSendHeaders`) |
| Заголовки **ответа** (условие) | частично (`responseHeaders` **Chrome 128+**; ⚠️ «полублок» — сервер запрос уже обработал, страница получит blocked-ответ; ⚠️ Chrome 121–127 игнорировали условие и блокировали всё) | частично (`onHeadersReceived`, будущие) | да | да (`requestStage: Response`) | да (`cancel`/`redirectUrl` в `onHeadersReceived`); ⚠️ DNR `responseHeaders` в Firefox **нет** (bug 1877486 NEW) |

| «N-й запрос к /api/x» | нет | частично (наблюдаемый не блокируется; параллельные проскакивают; `updateSessionRules` асинхронен) | **да** (счётчик синхронно в странице) | **да** (каждый запрос ждёт решения) | **да** (счётчик в `storage.session`, async-листенер ждёт чтения) |
| «B только после A (2xx)» | нет | частично (гонка при параллельных A/B) | да | да | да |
| «Один раз, потом пропускать» | нет | частично (детект по `onErrorOccurred` `ERR_BLOCKED_BY_CLIENT` — не отличить своё правило от чужого; параллельные копии блокируются все) | да | да | да |
| «Окно 30 с после клика» | — | да (content script → session rule с `tabIds` + `expiresAt`/`alarms`) | да | да | да |

| Mock тела/статуса | только redirect на `data:` (всегда 200) | нет | да | да | тело — StreamFilter (FF only, MV3 нужен `webRequestFilterResponse`); статус — нет |

## 2. Платформенные факты, на которые опирается архитектура

### 2.1 Chrome DNR (справочник 2026-09-11, `declarative_net_request.webidl` main)

- Условия: `urlFilter`, `regexFilter`, `isUrlFilterCaseSensitive`, `resourceTypes`, `requestMethods`, `initiatorDomains`, `requestDomains`, `topDomains` (145), `domainType`, `tabIds` (session only), `responseHeaders`/`excludedResponseHeaders` (128). С Chrome 145 — enum `RuleConditionKeys` для feature-detection.
- Стадии оценки: (1) до запроса — priority, при равном `allow > block > upgradeScheme > redirect`; (2) перед отправкой заголовков — `modifyHeaders` request; (3) **после получения ответа** — правила с `responseHeaders`. Дословно из справочника: *«A block or redirect rule with a response headers condition will still run – but cannot actually block or redirect the request… the page which made the request receiving a blocked response and Chrome terminating the request early»*. Для POST side-effect уже случился.
- ⚠️ **Статус-код**: в `request_params.cc` матчинг идёт через `HttpResponseHeaders::HasHeader/EnumerateHeader`; статусная строка там не заголовок, `:status` не виден. Косвенный обход — если сервер на 500 отдаёт характерный заголовок (`content-type: text/html` вместо JSON, `x-error`) — ненадёжно.
- Лимиты (не менялись с Chrome 120/121): dynamic 30 000 (unsafe 5 000), session 5 000, regex 1 000 на тип, static rulesets 100/50 enabled, `getMatchedRules` 20 вызовов/10 мин. Session — в памяти, гибнут при рестарте браузера и обновлении расширения; dynamic — персистентны; **оба переживают остановку SW**.
- ⚠️ Отладка в проде: `onRuleMatchedDebug` и `testMatchOutcome` — только unpacked; `declarativeNetRequestFeedback` — «ignored for extensions installed from the Chrome Web Store». Единственный продакшен-способ узнать о срабатывании — `getMatchedRules` + `activeTab` (жест пользователя) или косвенно `webRequest.onErrorOccurred` с `net::ERR_BLOCKED_BY_CLIENT` (без указания, чьё правило). Отсюда: для «Test URL against rule» нужен **собственный JS-матчер**, повторяющий семантику `urlFilter` (так у Requestly `ruleMatcher.ts` и Netify).
- Прочее: DNR не видит ответы `onfetch` service worker'а *страницы*; блокирует запросы других расширений (обход `excludedTabIds:[-1]`); `modifyHeaders` теряется на серверном редиректе (WECG #694); порядок при равном priority не стандартизирован — задавать явно.
- Бейдж-счётчик без доп. разрешений: `setExtensionActionOptions({displayActionCountAsBadgeText: true})`.

### 2.2 Chrome webRequest MV3 (2026-09-11)

- `webRequestBlocking` — только policy-installed (enterprise; планов на удаление нет — Chrome, 2025-02-21). Остальное без изменений: `onBeforeRequest` (`requestBody`), `onBeforeSendHeaders`, `onHeadersReceived` (**`statusCode`**, `responseHeaders`), `onCompleted` (`statusCode`), `onErrorOccurred` (`error`). Гарантия: последним всегда `onCompleted` или `onErrorOccurred`.
- Официальный паттерн «Adapt rules based on observed requests… blocked **in the future**». Латентность `updateSessionRules` **не документирована**; цепочка событие → IPC → (холодный старт SW) → `updateSessionRules` → переиндексация в UI-потоке; один update на расширение за раз (сериализация). Подтверждённая гонка: dynamic-правила не применяются к первому запросу после холодного старта Chrome (crbug 349653211).
- Как это используют в проде: Requestly по событию page-script ставит session-правило `{urlFilter: "|<exact url>|", tabIds:[tab], requestMethods}`, а на `onErrorOccurred` (CSP) — правило на снятие CSP для вкладки. Работает, когда между наблюдением и следующим запросом есть «человеческая» пауза.
- Приём для надёжности: держать **блокирующее** правило постоянно и управлять **allow-исключениями** (выше priority) — тогда неопределённость ошибается в сторону блокировки, что для chaos-тестов приемлемее.

### 2.3 `chrome.debugger` + CDP `Fetch` (2026-09-11, `debugger_api.cc` main)

- `Fetch.enable({patterns:[{urlPattern, resourceType, requestStage:'Request'|'Response'}]})` → `Fetch.requestPaused` (на Response: `responseStatusCode`, `responseHeaders`) → `failRequest(errorReason)` / `fulfillRequest(responseCode, headers, body)` / `continueRequest` / `continueResponse` (experimental). Единственный механизм Chrome с детерминированным порядком и реальным статусом для *всех* типов ресурсов, включая навигации и статику; воркеры — через `Target.setAutoAttach` (125+).
- **Chrome 118+: активная debugger-сессия держит SW живым** (`IncrementServiceWorkerKeepaliveCount(Activity::DEBUGGER)`) — in-memory счётчики безопасны, пока attach жив.
- ⚠️ Инфобар глобальный (`BrowserInfoBarManager::ShowGlobally`), закрывается через 5 с после detach всех таргетов; «Cancel» → `onDetach(canceled_by_user)`. Скрыть — только `--silent-debugger-extension-api` или policy-install (запрос пер-расширенного allowlist crbug 40815062 открыт). Enterprise `runtime_blocked_hosts`/DLP → attach падает.
- ⚠️ Расхождение документации и кода: справочник говорит, что открытие DevTools детачит расширение; `DevToolsAgentHostImpl` поддерживает несколько сессий, а ошибка «Another debugger is already attached» — только для *того же* расширения. Взаимодействие с DevTools «Request conditions» не описано — тестировать (§9).
- Overhead: замер 2026-09-12 — сам attach CDP снижает throughput `fetch()`-аплоадов с typed-array телами в 17–21× (Playwright/Puppeteer). Следствие: attach только на выбранную вкладку, только пока есть активные debugger-правила, паттерны максимально узкие. Paused-запросы висят, если логика упала — detach в `finally`.
- Известная дыра: `Fetch.requestPaused` не приходит для Document при первом attach к новой/перезагруженной вкладке (crbug 40811878).
- CWS: отдельного запрета нет; реальные примеры с `debugger` — **Network Overrides API (DevTools)** v2.3.0 (`["storage","debugger"]` + `<all_urls>`, в листинге: «required to intercept and fulfill requests through the Chrome DevTools Protocol», мокает статусы/задержки/failures — ровно наш профиль), Claude in Chrome, BrowserStack Toolkit, Leapwork. В этом репо прецедент уже есть — `perf` (opt-in через `optional_permissions`, PLAN.md §8).

### 2.4 MAIN-world патч `fetch`/XHR

- `scripting.registerContentScripts([{world:'MAIN', runAt:'document_start', allFrames:true, matches}])` — патч гарантированно до кода страницы. ⚠️ CSP страницы применяется к MAIN-world — никакого `eval`/`new Function` внутри.
- Так работают Requestly (`XMLHttpRequest.prototype` patch) и tweak (подмена `Response` со `status`, `defineProperty` на XHR `status/responseText`, delay). MSW-подобный in-page interceptor.
- Покрытие: `fetch`/XHR (+ `WebSocket`, `EventSource`; `sendBeacon` — только `return false`). **Не ловит**: навигации, `<img>/<script src>/<link>/@import`, шрифты, `<video>`, запросы Web/Service Worker'ов, prefetch, iframe-документы, запросы до инъекции. Обнаружим сайтом (`fetch.toString()` без `[native code]`, сравнение с чистым iframe-realm) — для dev/QA приемлемо, в описании честно.
- Плюс: счётчики и последовательности синхронно в странице — ноль гонок. Минус: DevTools Network показывает *реальный* ответ, а приложение — подменённый.

### 2.5 Service worker и состояние

- SW: 30 с простоя, 5 мин на операцию; `storage.session` 10 MB (112+), переживает рестарт SW, не рестарт браузера; нет атомарного инкремента → lost update при двух `onCompleted` подряд. `alarms` ≥ 30 с (120+).
- Паттерны (проверенные в этом репо на `adblock`/`blur` — Web Lock вокруг RMW): in-memory `Map` + write-through в `storage.session`; инициализация из storage **до** обработки первого события (listeners регистрируются синхронно на верхнем уровне, обработчики ждут промис init); все мутации через `navigator.locks.request('netblock-state', …)`; детерминированные id session-правил (`ruleId*1000 + slot`) + сверка с `getSessionRules()` при старте; правила с `tabIds` чистить на `tabs.onRemoved`; таймеры — `expiresAt` в состоянии + `alarms`, короткие точные окна — в content script.

### 2.6 Firefox (mozilla-central tip 2026-09-15, Bugzilla на 2026-09-15)

- ⚠️ **Blocking webRequest сохранён в MV3 и не на deprecation path** (Mozilla 2025-02-25; API-посты Firefox 149–153 без ограничений). `cancel` допустим в `onBeforeRequest`, `onBeforeSendHeaders`, **`onHeadersReceived`**, `onAuthRequired`; `redirectUrl` — в `onBeforeRequest` и `onHeadersReceived`; `WebRequest.sys.mjs::applyChanges` применяет их независимо от вида события. Blocking-листенер может вернуть **Promise** → можно читать `storage.session` внутри; незавершённый Promise удерживает event page от выгрузки.
- Изменить статус-код нельзя (в `BlockingResponse` нет поля). «Подмена при 500»: `redirectUrl` на `data:` (Firefox явно разрешает) или на `moz-extension://` (нужен `web_accessible_resources`), либо тело через `filterResponseData` (MV3: `webRequestFilterResponse`, 110+).
- `webRequest`/`webRequestBlocking`/`webRequestFilterResponse` — `OptionalPermissionNoPrompt`; предупреждение даёт только `<all_urls>`. Host permissions в MV3 (127+) показываются при установке, но отзываемы → проверять `permissions.contains`; новые хосты при апдейте не промптятся (bug 1893232); `activeTab` **не** даёт webRequest (bug 1617479). Если `filter.urls` не пересекается с выданными origin — события молча не приходят.
- DNR в Firefox: **нет `responseHeaders`** (bug 1877486 NEW), **нет `onRuleMatchedDebug`/`getMatchedRules`** (bugs 1745773/1745765 ASSIGNED), `testMatchOutcome` за префом; regex — JS `RegExp`, не RE2; лимиты dynamic 5 000 / session 5 000 / regex 1 000 / enabled rulesets **20**; `declarativeNetRequest` — с промптом и **не может быть optional**. DNR имеет приоритет над webRequest-листенерами. → в Firefox DNR нам не нужен вообще (как в `adblock`).
- Фон: **`background.service_worker` не поддерживается** (bug 1573659 meta NEW) — event page `background.scripts`, idle 30 с; удерживают DevTools, native ports, незавершённые Promise, StreamFilter. WXT это разводит сам (уже в `adblock`).
- Android: webRequest blocking + StreamFilter + DNR поддерживаются; `gecko_android: {}` обязателен; **нет** `menus`/`contextMenus`, `sidebarAction`, `devtools`, `windows`, `commands`; popup — пункт меню; `options_ui` во вкладке; пользователь не управляет host permissions (bugs 1820867/1812125). `data_collection_permissions` на Android — 142+.

## 3. Что взяли у существующих инструментов

Полная таблица (14 инструментов: Requestly, tweak, Netify, ModHeader, Resource Override, Mokku, ajax-tools, Header Editor, Request Control, uBOL, AdGuard MV3, Chrome/Firefox DevTools, Charles/Proxyman/mitmproxy) — в отчёте C; здесь — выводы.

**Берём:**
- **Многодвижковая схема Requestly** (DNR + наблюдающий webRequest + MAIN-world page-script) с явным полем `engine` — лучшая база; чиним её слабые места (§4).
- **Netify** как эталон debugger-движка: `FetchRuleStore.getRequestPatterns()` подписывает только нужные `requestStage`, 14 CDP `errorReason` для «fail», лог `NetworkLogEntry{…, modification:{ruleId, type, stage}}`, скрипты в `sandbox.html`. Лицензия BSD-2 — идеи переиспользуемы.
- **Модель stateful-правил** из тестовых инструментов: MSW `once`; Playwright `times` + `route.fetch()→fulfill` («получить настоящий ответ и переопределить»); Dev Proxy `nth` (2026-09-14); MockServer chaos-profile (`errorProbability`, `succeedFirst`, `failRequestCount`, `outageAfterMillis`, `outageDurationMillis`, `seed`, `retryAfter`); WireMock scenarios (`requiredScenarioState`/`newScenarioState`); Proxyman `SharedState`; mitmproxy flow-filter (`~c 500 & ~u /api`) — как синтаксис импорта/«advanced»-поля.
- **UX-паттерны**: группы/профили с toggle на правило и группу, порядок = приоритет (drag), «создать правило из запроса» в собственном сетевом логе, счётчик срабатываний у правила с временем последнего, бейдж на иконке, «Test URL against rules», scope Active tab / Global, честная подпись «что покажет DevTools» у page-правил (open-resource-override-mv3), инъекция **только на включённых сайтах** (Mokku — только `localhost` до явного включения; uBOL — per-site permission).
- **Chrome DevTools «Request conditions» (Chrome 145)** — подтверждает спрос: Block + Throttle per-URL, first-match, но выключается при закрытии DevTools и не умеет статус — наш инструмент закрывает именно эти дыры.

**🔴 Не копируем:**
- Скрытая телеметрия при широких permissions — **ModHeader 7.0.18 удалён из CWS и Edge (июль 2026)** за спящий SDK сбора доменов; 1.6 млн установок. Ноль сети в расширении, CSP без `connect-src`.
- Delay через редирект на сервер вендора (Requestly `app.requestly.io/delay/…`) — утечка URL, ломает CORS/cookies.
- Молчаливое расхождение DevTools ↔ приложение (Requestly, tweak).
- Только `debugger` как единственный движок (Netify) — постоянный инфобар.
- Content script `<all_urls>` в `document_start` всегда (Requestly `client.cs.js`).
- `new Function` для пользовательских скриптов в контексте расширения (ajax-tools).
- Отсутствие статуса исходного ответа в JS-хуке (tweak `hook`, Requestly code-mode) — именно он нужен для «заменить, если 5xx»; в нашей модели `status/headers/body` ответа передаются всегда.
- Лимит правил во free-плане и привязка к веб-аккаунту.

## 4. Архитектура: один формат правила — три движка (Chrome) / один (Firefox)

```
┌──────────────── правило (JSON, §5) ────────────────┐
│ match · state · action · engine: auto|dnr|page|debugger │
└───────────────┬──────────────┬──────────────┬──────────┘
                │              │              │
        Chrome  ▼              ▼              ▼            Firefox
   ┌── L1 DNR ──┐  ┌── L2 page ──┐  ┌── L3 debugger ──┐  ┌── webrequest ──┐
   │ session/   │  │ MAIN-world  │  │ CDP Fetch,      │  │ blocking       │
   │ dynamic,   │  │ fetch/XHR   │  │ opt-in на вкладку│  │ onBeforeRequest│
   │ tabIds     │  │ патч        │  │                 │  │ onHeadersRecv. │
   └────────────┘  └─────────────┘  └─────────────────┘  └────────────────┘
   stateless +      точные счётчики    реальный статус,    всё, без гонок
   «широкие окна»   для XHR/fetch,     навигации/статика/  (статус — cancel,
   без host perms   клиентская подмена воркеры, fail-reason не подмена)
```

**Правила выбора `engine: auto` (Chrome):**
1. `action ∈ {block, redirect, headers}` и нет `match.response.*`, нет `state.*` → **L1 DNR**.
2. `match.response.headers` без `status`/`body` → **L1 DNR** при `RuleConditionKeys` содержит `responseHeaders` (145+) или `minimum_chrome_version ≥ 128`; иначе → L2/L3.
3. `state.*` с «широким окном» (`window`, `skipFirst`→«все последующие», `afterRule` без требования «сразу») → **L1 DNR** реактивно (наблюдение → `updateSessionRules`), помечается в UI как *approximate*.
4. `match.response.status|body`, `action ∈ {mock, modifyResponse, delay}`, точные `state.nth|times|once|scenario` и `resourceTypes ⊆ {xmlhttprequest, websocket}` → **L2 page**.
5. То же для не-AJAX ресурсов, либо `action ∈ {fail(reason), throttle, breakpoint}` → **L3 debugger** (если пользователь включил Network-level mode на вкладке; иначе правило показывается как «требует Network-level mode» и не активно).
6. **Firefox**: всё → `webrequest`; `action: mock/modifyResponse/fail(reason)/throttle` деградируют (mock тела — через StreamFilter, статус не меняется — UI это говорит).

**Наблюдение (Chrome)** — `webRequest` non-blocking на выданных хостах: `onHeadersReceived.statusCode` для реактивных правил и лога, `onErrorOccurred` (`ERR_BLOCKED_BY_CLIENT`) для счётчика L1-срабатываний (помечать «≈», как в `adblock` PLAN.md §5), `onCompleted` для `afterRule`.

**Инъекция L2** — только на сайтах, где пользователь включил расширение (`optional_host_permissions` + `permissions.request` из popup, как в `adblock`/`devdata`), регистрируется динамически `registerContentScripts` с `matches` = выданные origin. Никакого install-time `<all_urls>` content script — это принцип волн 2–3 (README).

**L3** — кнопка «Network-level mode» в popup на текущей вкладке: `permissions.request({permissions:['debugger']})` → `attach` → `Fetch.enable` с паттернами, собранными из активных L3-правил → в UI объяснение баннера. `onDetach(canceled_by_user)` → деградация до L1/L2 с уведомлением. Detach при закрытии вкладки, выключении режима, отсутствии активных L3-правил > N с.

**Честность UI** (конвенция дома PLAN.md §18a): у каждого правила бейдж движка; у L2 — подпись «DevTools покажет реальный ответ»; у реактивных L1 — «срабатывает со следующего запроса»; у L3 — «показывает баннер отладки»; счётчики L1 — «≈».

## 5. Модель правила (набросок схемы v1)

```jsonc
{
  "id": "r_8f1c", "name": "Checkout: 503 после 3-го вызова", "enabled": true,
  "group": "checkout-chaos",              // toggle как набор
  "priority": 100, "stopProcessing": true, // first-match по priority, затем порядок списка

  "scope": { "tabs": "active" | "all" | [123], "pageDomains": ["shop.example.com"], "excludePageDomains": [] },

  "match": {
    "url": { "key": "url"|"host"|"path", "op": "contains"|"equals"|"wildcard"|"regex", "value": "*/api/checkout*" },
    "urlExclude": [{ "op": "contains", "value": "/health" }],
    "methods": ["POST"],
    "resourceTypes": ["xmlhttprequest"],          // DNR enum; в FF маппится на свои типы
    "requestHeaders": [{ "name": "x-feature", "op": "equals", "value": "beta" }],
    "requestBody": { "path": "operationName", "op": "equals", "value": "Checkout" },  // GraphQL
    "response": {                                  // → engine page|debugger|webrequest (DNR только headers, 128+)
      "status": { "op": "in", "value": ["5xx", 429] },
      "headers": [{ "name": "content-type", "op": "contains", "value": "json" }],
      "body": { "op": "regex", "value": "\"error\"" }
    }
  },

  "state": {                                       // счёт по ключу; отсутствие = stateless
    "key": "rule"|"url"|"tab"|"rule+tab", "resetOn": "navigation"|"session"|"manual",
    "once": false, "times": 3, "nth": { "n": 3, "every": false },
    "skipFirst": 5, "thenFail": 10,
    "probability": { "p": 0.3, "seed": 42 },       // воспроизводимый рандом
    "window": { "afterMs": 5000, "forMs": 10000 },
    "scenario": { "name": "login", "requires": "Started", "sets": "LoggedIn" },
    "afterRule": "r_login_ok"
  },

  "action": {
    "type": "block"|"fail"|"redirect"|"headers"|"mock"|"modifyResponse"|"delay"|"throttle"|"breakpoint",
    // fail: { "reason": "TimedOut" }           — CDP errorReason; page: TypeError + имитация; FF: cancel
    // mock: { "status": 503, "headers": {}, "body": "…", "passthrough": false, "delayMs": 800 }
    // modifyResponse: { "status": 500, "patch": [{ "op": "replace", "path": "/items", "value": [] }] } — реальный ответ запрашивается
    // headers: { "request": [{ "op": "set", "name": "…", "value": "…" }], "response": [] }  🔴 не трогать CSP (AMO)
  },

  "engine": "auto"|"dnr"|"page"|"debugger"|"webrequest",
  "meta": { "createdFrom": "log", "updatedAt": 1757900000 }
}
```

Пользовательский JS-предикат в v1 **не входит**: в Chrome — только через `chrome.userScripts` (138+, пер-расширенный тумблер «Allow User Scripts», выключен по умолчанию для новых установок), в Firefox — 🔴 запрещён политикой для не-менеджеров. Regex/DSL/счётчики — данные (конфигурация), не remote code. Импорт: свой JSON, ModHeader-профили, Requestly, HAR → правила; экспорт — JSON.

## 7. Stateful-состояние: где живёт и как не сломать

| Что | Chrome | Firefox |
|---|---|---|
| Точные счётчики (`nth`, `times`, `once`, `scenario`) | L2: в странице (per-document, зеркалируется в SW через `runtime.sendMessage`); L3: в SW (debugger держит его живым) | В event page, чтение/запись `storage.session` внутри async blocking-листенера |
| Реактивные (L1 «после N — все», `window`, `afterRule`) | `storage.session` + Web Lock; `expiresAt` + `alarms` (≥30 с) | То же, но без гонок |
| Сброс | `resetOn: navigation` → `webNavigation` не нужен: `tabs.onUpdated(status==='loading')` или `onBeforeRequest(main_frame)`; `session` → рестарт браузера; `manual` → кнопка | То же |
| Восстановление после рестарта SW | init из `storage.session` до первого события; сверка `getSessionRules()` с сохранённым; `tabs.onRemoved` → снять `tabIds`-правила | event page перезапускается по blocking-событию; состояние в `storage.session` |
| Воспроизводимость | `probability.seed` → детерминированный PRNG per rule+key | то же |

## 9. Открытые вопросы — проверить эмпирически до дизайна

1. **Латентность `updateSessionRules`** (мс от события `onCompleted` до применимости правила) на холодном и тёплом SW — определяет, какие `state.*` можно честно отдавать L1.
2. **CDP `Fetch` и WebSocket-хендшейк** — в `fetch_handler.cc`/`devtools_url_loader_interceptor.cc` упоминаний нет; если не ловит, `resourceTypes: websocket` в L3 надо запретить.
3. **DevTools открыт + `debugger.attach`**: детач или сосуществование; что происходит с DevTools «Request conditions» одновременно с нашим `Fetch.enable`.
4. **`responseHeaders` + `block` в DNR**: как выглядит blocked-ответ для страницы (`ERR_BLOCKED_BY_CLIENT`?) и виден ли он в `onErrorOccurred` для счётчика.
5. **Firefox: `redirectUrl` на `data:` из `onHeadersReceived`** для XHR/fetch с CORS — доходит ли до страницы как успешный ответ.
6. **Chrome 145 `topDomains`** — дата стабильного релиза не подтверждена; feature-detect через `RuleConditionKeys`.
7. Как WXT собирает `optional_permissions: ['debugger']` + `optional_host_permissions` в MV2-fallback Firefox (в `adblock` уже отмечено, что `optional_host_permissions` для MV2 WXT дропает).
